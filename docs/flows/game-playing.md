# Game Playing Flow

This guide explains how a frontend client should play a Stage 1 STS run through the backend API.

For card artwork and thumbnails, load `GET /api/sts/cardsImage` with the authenticated session. The response uses the same `CardDto[]` shape as `GET /api/admin/cards`, includes cards in public and game categories, excludes hidden categories and the default card cover, and is independent of the versioned STS gameplay JSON catalogue at `GET /api/sts/catalog/cards`.

The backend owns run state, map reachability, rewards, event effects, token grants, and persistence. The game client may render and simulate combat locally, but it must report node progress through the API so the backend can validate and advance the run.

## Authentication

All `/api/sts/**` routes require an authenticated browser session.

State-changing requests must include the normal CSRF header:

```http
X-XSRF-TOKEN: <csrf-token>
```

Use `GET /api/csrf` before the first POST if the frontend does not already have a token.

## Load Catalogs

Load the released config catalogs before rendering cards, characters, enemies, events, or local combat data:

```http
GET /api/sts/catalog/cards
GET /api/sts/catalog/characters
GET /api/sts/catalog/enemies
GET /api/sts/catalog/enemy-pool
GET /api/sts/catalog/events
```

`GET /api/sts/catalog/enemy-pool` returns the complete, unmodified `EnemyPool/EnemyPool.json` document from the latest release. It is separate from `/api/sts/catalog/enemies`, which returns the individual enemy definitions loaded from `EnemyData/*.json` (or the legacy enemy catalog).

The run itself stores the `dataVersion` returned by the latest released game config at creation time. Use that version as debug metadata and avoid mixing a saved run with assets from a different config release.

## Start Or Resume

On page load, check whether the player already has an active run:

```http
GET /api/sts/runs/current
```

Response when a run exists:

```json
{
  "hasRun": true,
  "run": {
    "runId": "6d0dffb4-8f39-4e8c-bdb1-33dfc4b2582b",
    "status": "Active",
    "dataVersion": "2026.1.0",
    "selectedCharacter": "Astro",
    "act": 0,
    "currentFloor": 0,
    "currentNodeId": 0,
    "enteredNodeId": null,
    "player": {
      "maxHp": 80,
      "currentHp": 80
    },
    "runInventory": {
      "gold": 0,
      "deck": [],
      "relics": []
    },
    "map": {
      "nodes": []
    },
    "pendingRewards": [],
    "activeEvent": null
  }
}
```

If `hasRun` is false, show character selection and start a run. Calling this endpoint while a run is already active safely returns that existing run without replacing it:

```http
POST /api/sts/runs
Content-Type: application/json
X-XSRF-TOKEN: <csrf-token>

{
  "character": "Astro",
  "clientVersion": "web-2026.1.0"
}
```

The response is a full run state. The backend builds the starting deck from `catalogs/cards.json` and creates the starting relic for the selected character.

## Run State Model

The important state fields are:

| Field | Meaning |
| --- | --- |
| `status` | `Active`, `Failed`, or `Abandoned`. Only `Active` runs can advance. |
| `currentNodeId` | Last completed map node. New nodes must be reachable from this node's `nextIds`. |
| `enteredNodeId` | Node currently in progress. `null` means the player is between nodes. |
| `player` | Backend-owned HP state: `maxHp` and `currentHp`. |
| `runInventory` | Run-local gold, deck card instances, and relic instances. |
| `map.nodes` | Generated map nodes with `id`, `floor`, `type`, `visited`, `completed`, and `nextIds`. |
| `pendingRewards` | Unclaimed rewards generated by completed nodes or events. |
| `activeEvent` | Current event payload when the entered node is an event. |

Store `runId` in UI state, but do not treat local state as authoritative. Refresh with `GET /api/sts/runs/current` after reloads, conflict responses, or suspicious local state.

## Enter A Node

The user may enter only a node listed in the current node's `nextIds`.

```http
POST /api/sts/runs/{runId}/nodes/{nodeId}/enter
Content-Type: application/json
X-XSRF-TOKEN: <csrf-token>

{
  "clientKnownCurrentNodeId": 0
}
```

`clientKnownCurrentNodeId` is optional, but recommended. If the frontend is stale, the backend returns a conflict instead of entering the wrong node.

Response:

```json
{
  "accepted": true,
  "runId": "6d0dffb4-8f39-4e8c-bdb1-33dfc4b2582b",
  "nodeId": 1,
  "nodeType": "Combat",
  "activeEncounter": {
    "encounterInstanceId": "encinst_...",
    "encounterId": "slime_group",
    "enemyIds": ["Slime", "Slime"],
    "playerHpBefore": 80,
    "startedAt": "2026-07-14T08:00:00Z"
  },
  "eventId": null,
  "activeEvent": null
}
```

For `Combat`, `Elite`, and `Boss` nodes, the backend creates `activeEncounter`. Use its `encounterInstanceId` when completing the combat.
When `EnemyPool/EnemyPool.json` exists in the release, the backend chooses the encounter from that pool and derives combat, elite, and boss tables from the pool flags.

For `Event` nodes, the backend creates `activeEvent` instead. Event nodes are completed through the event choice route, not the node completion route.

## Complete Combat Nodes

After local combat finishes, submit the result:

```http
POST /api/sts/runs/{runId}/nodes/{nodeId}/complete
Content-Type: application/json
X-XSRF-TOKEN: <csrf-token>

{
  "encounterInstanceId": "encinst_...",
  "result": "Victory",
  "turnCount": 4,
  "playerHpAfter": 72,
  "damageTaken": 8,
  "enemiesDefeated": ["Slime", "Slime"],
  "deckHash": "optional-client-debug-value"
}
```

For encounter nodes, the backend validates:

- The submitted `encounterInstanceId` matches the active encounter.
- `turnCount` is greater than zero.
- `damageTaken` is zero or greater.
- `playerHpAfter` is between zero and `maxHp`.
- On `Victory`, `enemiesDefeated` exactly matches the encounter enemy list.

On victory, the backend marks the node completed, updates HP, generates pending rewards, and grants account tokens when configured for the node type.

Response:

```json
{
  "accepted": true,
  "runId": "6d0dffb4-8f39-4e8c-bdb1-33dfc4b2582b",
  "currentNodeId": 1,
  "player": {
    "maxHp": 80,
    "currentHp": 72
  },
  "runInventoryPatch": {},
  "accountInventoryPatch": {
    "tokenDelta": 1
  },
  "pendingRewards": [
    {
      "rewardId": "reward_...",
      "type": "Gold",
      "claimed": false,
      "amount": 21
    }
  ],
  "mapPatch": {
    "visitedNodeIds": [0, 1],
    "completedNodeIds": [0, 1],
    "currentNodeId": 1,
    "enteredNodeId": null
  }
}
```

If `result` is not `Victory`, the backend marks the run `Failed`, clears the active node, and returns a completion response. Refresh the run and show the failure state.

## Claim Rewards

Rewards stay in `pendingRewards` until claimed. Claim them one at a time:

```http
POST /api/sts/runs/{runId}/rewards/{rewardId}/claim
Content-Type: application/json
X-XSRF-TOKEN: <csrf-token>

{}
```

For `CardChoice`, the request must include a selected card:

```json
{
  "selectedCardId": "Strike"
}
```

Supported reward types:

| Type | Claim behavior |
| --- | --- |
| `Gold` | Adds `amount` to `runInventory.gold`. |
| `CardChoice` | Adds one new card instance for `selectedCardId`. |
| `Relic` | Adds one relic instance for `relicId`. |
| `BaseRelicUpgrade` | Updates the matching base relic instance stage. |

Response:

```json
{
  "accepted": true,
  "runInventory": {
    "gold": 21,
    "deck": [],
    "relics": []
  },
  "pendingRewards": []
}
```

Use the returned `runInventory` and `pendingRewards` as the new local state.

## Handle Events

When entering an `Event` node, the response includes `activeEvent`:

```json
{
  "eventInstanceId": "evtinst_...",
  "nodeId": 3,
  "eventId": "strange_machine",
  "id": "strange_machine",
  "title": "Strange Machine",
  "description": "A machine hums in the room.",
  "imageName": "machine.png",
  "status": "Active",
  "startedAt": "2026-07-14T08:05:00Z",
  "options": [
    {
      "optionId": "repair",
      "text": "Repair it",
      "iconName": "wrench",
      "completionMessage": "The machine rewards you.",
      "entries": [],
      "selectionRequirements": []
    }
  ]
}
```

Submit the selected option:

```http
POST /api/sts/runs/{runId}/events/{eventInstanceId}/choose
Content-Type: application/json
X-XSRF-TOKEN: <csrf-token>

{
  "optionId": "repair",
  "selectedCardInstanceIds": []
}
```

Some event options include `selectionRequirements`. For `DeckCardPick`, the frontend must let the player select exactly `count` card instance IDs from `runInventory.deck` and pass them as `selectedCardInstanceIds`.

Event entries are applied by the backend. Supported effects include damage, heal, gold reward, max HP gain/loss, card reward, relic reward, and card removal.

Successful event choices complete the event node and return:

```json
{
  "accepted": true,
  "eventInstanceId": "evtinst_...",
  "eventCompleted": true,
  "player": {
    "maxHp": 85,
    "currentHp": 77
  },
  "runInventoryPatch": {
    "goldDelta": 10,
    "removedCardInstanceIds": [],
    "addedCards": [],
    "addedRelics": [],
    "updatedRelics": []
  },
  "accountInventoryPatch": {
    "tokenDelta": 0
  },
  "pendingRewards": [],
  "mapPatch": {
    "visitedNodeIds": [0, 3],
    "completedNodeIds": [0, 3],
    "currentNodeId": 3,
    "enteredNodeId": null
  },
  "completionMessage": "The machine rewards you."
}
```

## Retire After An Act

When the player completes a boss and chooses to stop instead of continuing to the next act, call:

```http
POST /api/sts/runs/{runId}/retire
X-XSRF-TOKEN: <csrf-token>
```

The request has no body. The backend requires a completed `Boss` as the current node and rejects retirement while a node, encounter, or event is active. It calculates the accumulated score from the persisted run and the versioned `gameplay/run_score_rewards.json` rules. The client must never send a score or token amount.

```json
{
  "accepted": true,
  "runId": "70d30ad4-47c0-4d30-8719-fbe76031c429",
  "status": "Retired",
  "score": 665,
  "tokensGranted": 33,
  "tokenBalance": 40
}
```

Retirement and token credit happen in one transaction. Retrying the same request returns the stored score and token grant without crediting the account again.

If the player continues to the next act, do not call this endpoint. No tokens are granted at that boundary; the active run and its accumulated scoring state continue into the next act.

## Reset A Run

To abandon an active run:

```http
POST /api/sts/runs/{runId}/reset
X-XSRF-TOKEN: <csrf-token>
```

Success returns `204 No Content` and marks the run `Abandoned`.

## Recommended Client Loop

1. Fetch CSRF and session state.
2. Load catalogs and the active game config release.
3. Call `GET /api/sts/runs/current`.
4. If no active run exists, start one with `POST /api/sts/runs`.
5. Render reachable nodes from `map.nodes[currentNodeId].nextIds`.
6. Enter a selected reachable node.
7. For combat nodes, run local combat, then complete the node.
8. For event nodes, render event options, gather required selections, then choose an option.
9. Render and claim all pending rewards.
10. Repeat from reachable node selection.
11. After a boss, either continue without a token grant or retire the run through `POST /retire`.
12. On conflict or validation errors, refresh `GET /api/sts/runs/current` and reconcile the UI.

## Error Handling

Common responses:

| Status | Typical cause | Client action |
| --- | --- | --- |
| `400 Bad Request` | Invalid request body, invalid combat result, unknown event entry, invalid reward choice. | Keep the current screen, show a recoverable error, and inspect the request payload. |
| `401 Unauthorized` | Missing or expired login session. | Redirect to login/session recovery. |
| `403 Forbidden` | Missing CSRF token or insufficient access. | Refresh CSRF/session and retry only when appropriate. |
| `404 Not Found` | Run, node, or reward is not owned by the user or does not exist. | Return to run selection or refresh current run. |
| `409 Conflict` | Stale client position, wrong active encounter/event, inactive run, unreachable node, node already completed, or retirement attempted outside an act boundary. | Refresh run state and rebuild the UI from backend state. |

Do not blindly retry state-changing requests after a conflict. Refresh first, then decide whether the user action is still valid.
